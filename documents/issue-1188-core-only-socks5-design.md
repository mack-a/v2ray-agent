# Issue #1188：SOCKS5 入站自动补齐 sing-box 与必要依赖实现方案

- 日期：2026-10-30
- 状态：中英文安装脚本已实现；本地隔离回归及真实核心验证完成，Linux 实机验收待执行
- 仓库基线：`ade6c61`，脚本显示版本 `v3.5.32`
- 需求来源：[mack-a/v2ray-agent#1188](https://github.com/mack-a/v2ray-agent/issues/1188)
- 涉及文件：`install.sh`、`shell/install_en.sh`、`checks/socks5_standalone_test.py`

## 1. 需求与推荐方案

Issue 描述的是：新机器进入 `vasma → 11 → 4 → 2`，希望只安装 SOCKS5 入站，却被要求先通过主菜单 1/2 安装其他代理协议。以下具体函数设计属于本方案建议。

**仅保留“安装 SOCKS5 入站”这一条安装路径：在该操作内部自动补齐 sing-box、运行配置和必要依赖，然后启动入站服务。SOCKS5 入站仅由 sing-box 实现。**

用户仍按原菜单操作：

```text
vasma → 11.分流工具 → 4.Socks5分流 → 2.Socks5入站 → 1.安装Socks5入站
  → 自动准备 sing-box 和必要依赖
  → 补齐基础配置并生成 SOCKS5 入站、路由
  → 检查配置并启动服务
```

不新增“仅安装内核”菜单、独立安装命令或供用户使用的空内核安装模式。内核准备函数只是 SOCKS5 入站安装的内部步骤，成功标准是入站可用，而不是下载完成。

该流程不要求域名、TLS 证书、Nginx、伪装站或订阅。没有 sing-box 时自动安装，已有可用 sing-box 时复用。即使机器上只有 Xray，SOCKS5 入站也另用 sing-box；不下载、升级 Xray，不生成 Xray SOCKS5 入站，不修改 Xray 配置或重启 Xray 服务。原有 SOCKS5 出站能力保持现状。

**已有 sing-box 直接复用，只有缺少二进制时才下载安装。** 已安装或正在运行的内核都不查询新版本、不提示升级、不替换二进制；在现有配置上补齐 SOCKS5 所需项，保留其他入站和规则。核心升级、旧配置迁移和并发控制均不在本功能范围内。

首期继续只管理一个 SOCKS5 入站，不扩展多入站、多落地机及协议级分流；后两项与现有 `socks5-multi-outbound-routing-design.md` 的出站设计分别实施。

## 2. 代码审计与根因

以下行号对应本次工作区，仅用于定位；实施时以函数名为准。英文脚本存在相同调用关系。

| 位置 | 当前行为 | 实现影响 |
| --- | --- | --- |
| `socks5Routing()`，约 8453 行 | `coreInstallType` 为空直接 `exit 0`，尚未显示出站/入站选择 | 新机器在公共入口就被拦截 |
| `socks5InboundRoutingMenu()`，约 8484 行 | 调用 `installSingBox → installSingBoxService → setSocks5Inbound → setSocks5InboundRouting → reloadCore` | 已有入站生成器可以复用，但缺少独立初始化与完整失败处理 |
| `installSingBox()`，约 2698 行 | 下载前调用 `readInstallType`；已安装时询问升级 | 下载不等于就绪，也不应在每次配置入站时询问升级 |
| `installTools()`，约 1345 行 | 安装通用工具，同时可能安装 Nginx、acme.sh | 不能直接作为最小安装的依赖入口 |
| `readInstallType()`，约 615 行 | sing-box 要求二进制和合并配置；但它位于“没有 Xray 二进制”的 `elif` 分支 | 残留 Xray 二进制会遮蔽有效 sing-box；首次合并前又无法识别 sing-box |
| `setSocks5Inbound()`，约 8697 行 | 通过核心生成 UUID，直接写入正式 JSON，再生成 resolve 规则 | 新机可能因路径变量未初始化而生成空凭据；输入失败时已可能开放端口/写入文件 |
| `singBoxMergeConfig()`，约 4430 行 | 补 DNS/HTTP Client，临时合并、check 后替换正式主配置 | 已有原子发布基础，但配置片段仍在正式目录修改 |
| `reloadCore()`，约 9039 行 | 重新识别安装状态，再重启识别到的核心 | 首次没有主配置时可能不启动 sing-box；混合安装会同时重启 Xray |
| `readConfigHostPathUUID()`，约 1078 行 | sing-box 没有普通前置时按 Reality 文件读取 UUID | 只有 SOCKS5 时可能读取 `config/.json` |
| `readInstallProtocolType()` / `showInstallStatus()` | 已读取 SOCKS5 编号 `20`，但状态页没有对应显示；混合安装补扫没有 SOCKS5 | 独立及混合安装的状态显示不完整 |

还存在两个必须处理的关联问题：

- `setSocks5InboundRouting()` 创建 `block` 出站，但没有生成 SOCKS5 未命中的拒绝规则，也没有设置拒绝默认出口。官方文档规定 `route.final` 为空时使用第一个出站，当前 `01_direct_outbound` 的存在使白名单无法仅靠一个 `block` 文件成立。
- 官方已于 sing-box 1.13.0 移除旧 `block` 出站。新流程必须使用 `action: "reject"`，不能继续调用 `addSingBoxOutbound block`。当前下载接口截至本次调研返回稳定版 `v1.14.4`；版本不能写死在下载逻辑中。

因此，仅删除 `socks5Routing()` 的检查不足以完成需求。

## 3. 菜单与操作行为

保留现有入站菜单和编号，不新增安装入口：

```text
11.分流工具 → 4.Socks5分流 → 2.Socks5入站

1.安装 SOCKS5 入站
2.查看分流规则
3.添加分流规则
4.查看入站配置
```

- `socks5Routing()` 允许未安装核心时显示菜单；“出站”分支保留已安装代理协议的检查，因为单独一个出站不能形成可用转发入口。
- “安装入站”内部调用准备函数，自动补齐必要项；无需再经过主菜单 1/2，也不询问选择 Xray 或 sing-box。
- 查看、修改规则和卸载分别检查实际 SOCKS5 文件是否存在；无配置时提示并返回，不触发安装。
- 已有 sing-box 直接复用，不调用会询问升级的安装分支；仅在二进制缺失时下载安装。已有二进制无法执行时明确报错，不自动替换或重装。
- 只有 SOCKS5 时显示“SOCKS5 入站”，不显示空的“已安装协议”或生成 VLESS/Reality 账号。依赖或配置准备失败时提示安装未完成，并允许从原入口重试。

## 4. sing-box 自动准备与安装状态

建议新增内部函数 `prepareSingBoxCoreForSocks5()`，由入站安装流程调用，负责依赖、目录、二进制存在性和可执行性检查；不单独暴露给用户，不负责收集入站参数、开放端口或重启服务。

### 4.1 依赖与目录

新增内部函数 `installSocks5InboundTools()`，只安装实际缺失的下载、解包、JSON、证书信任和端口检查工具：`curl`、`wget`、`tar`、`jq`、`ca-certificates`、`lsof`，以及复用防火墙逻辑实际要求的命令。Bash、基础文件工具和相应服务管理器作为运行前置检查。systemd 与 Alpine/OpenRC 分别判断，不能仅因系统上存在一个 `systemctl` 文件就认定可用。

按发行版使用当前包管理器变量，检查每个安装命令的返回值；依赖失败立即返回非零。最小流程不调用整个 `installTools()`，也不借用 Reality 协议编号来跳过 Nginx/证书。

沿用目录：

```text
/etc/v2ray-agent/sing-box/
  sing-box
  conf/
    config.json              # 已检查的合并配置
    config/                  # 正式配置片段
```

公共 `menu()` 目前仍会调用 `mkdirTools()` 创建订阅等目录；本次无需为“最小安装”重构全部目录初始化。验收重点是没有安装、启动 Nginx，没有申请证书或添加 TLS 定时任务。

### 4.2 二进制复用与首次下载

- 标准路径已有 sing-box 二进制时直接复用，即使它是较旧版本或当前正在运行，也不查询远端版本、不升级、不替换。可执行性检查失败则报错退出。
- 只有二进制缺失时，查询稳定版并复用 `installCoreRelease sing-box <version>` 的临时下载、解包、执行检查和发布流程；校验查询与下载结果。
- 配置能否使用，以本机现有内核执行 `merge/check` 的结果为准，不以“必须升级至 1.14.x”作为安装门禁。检查失败时保留原配置和服务并报告具体原因，本功能不自动升级内核，也不增加旧格式适配或迁移分支。
- 仓库现有 `singBoxMergeConfig()` 无条件生成共享 `http_clients`，而该能力从 1.14.0 起支持。SOCKS5 安装流程应按实际需要准备配置：不使用远程规则集时不额外引入共享 HTTP Client；需要它的配置由现有内核检查。不能为了复用一个 helper 而无条件增加配置版本要求。

### 4.3 状态识别

不新增与配置容易失配的“已安装”标记文件。区分以下事实：

| 状态 | 判断依据 | 行为 |
| --- | --- | --- |
| 未准备 | 无可执行二进制 | 安装依赖和内核 |
| 安装未完成或卸载后残留 | 二进制可用，但没有有效 SOCKS5 或其他业务入站 | 原入口重试时复用可用文件；不认定 SOCKS5 已安装，不自动启动空服务 |
| SOCKS5 已配置 | 二进制和有效合并配置存在，且有 `20_socks5_inbounds.json` 和对应规则 | 可以查看、修改、卸载入站；运行状态单独检查 |
| 混合部署 | 存在已识别的 Xray/sing-box 其他入站 | 增量添加 SOCKS5，保护现有配置和服务 |

调整 `readInstallType()`：独立探测两个核心，先判断有效的 Xray 配置，再判断 sing-box；保留现有 `coreInstallType=1/2` 含义与 Xray 优先规则。有有效 Xray 时 `configPath` 仍指向 Xray，SOCKS5 始终使用 `singBoxConfigPath`；残留无配置的 Xray 不遮蔽 sing-box。这里对 Xray 的判断只用于兼容已有部署，不新增任何 Xray 入站能力。仅有二进制或无业务入站的基础配置，不作为本功能安装成功的依据。

SOCKS5 事务使用显式的 sing-box 目标路径，不依赖 `readInstallType()` 在首次合并前推导出路径。没有安装状态时 `readInstallProtocolType()` 应直接返回，避免对空路径执行 `find`。没有普通协议/Reality 文件时，`readConfigHostPathUUID()` 也直接结束对应读取分支。混合部署补扫 SOCKS5 的编号和端口，状态页增加 `20` 的展示。

“内核存在”不等于“有可管理的代理账号”。账号、订阅、证书和添加代理端口等入口，须检查它们实际需要的协议/域名；对 SOCKS5-only 显示对应提示，避免落入空 UUID、空域名的配置生成。不扩展独立空内核的管理功能。

## 5. 配置生成与访问控制

### 5.1 输入与文件边界

沿用 `20_socks5_inbounds.json` 和 `socks5_inbound` tag；首期继续只管理一个 SOCKS5 入站。输入包含监听地址、端口、凭据、允许的来源 IP/CIDR、IPv4/IPv6 解析策略，以及全部目标或指定域名/rule-set。

保留当前随机 UUID 同时作为用户名/密码的交互，改为直接通过 sing-box 二进制生成，不依赖主核心类型；生成结果不能为空。收集输入时只记录“随机生成”的选择，内核准备完成后再实际生成并检查凭据。所有配置使用 `jq --arg/--argjson` 生成，避免引号、反斜线破坏 JSON。含凭据的片段、主配置和备份权限设为 `600`，暂存目录 `700`。

端口必须是 1～65535 的十进制整数，排除其他进程或入站占用；随机端口同样检查。修改时允许当前 SOCKS5 自己的端口。来源白名单必须非空且校验 IPv4/IPv6/CIDR 格式；不合法输入、取消或 EOF 不得写正式配置、安装服务或开放端口。不要直接复用会提前调用 `allowPort` 的 `initSingBoxPort()`，应拆分“取值/校验”和“应用防火墙”。

DNS、direct 出站以及实际需要的共享 HTTP Client 仅补缺项；发现相同 tag 被定义为不兼容对象时报错，不能覆盖其他功能的定义。基础配置与 SOCKS5 入站、路由一起在暂存目录生成，通过整体检查后统一提交，不先发布并启动一个没有入站的基础服务。

### 5.2 SOCKS5 专用规则

新增 `00_socks5_guard.json`，集中保存 SOCKS5 的 sniff、resolve、允许和最终拒绝规则。规则查看、修改和卸载统一使用这一结构；不生成或兼容旧的 `socks5_02_inbound_route.json`。

必须满足：

1. 所有规则都限定 `inbound: ["socks5_inbound"]`。
2. 未授权来源先拒绝；授权来源再执行必要的 sniff/resolve。
3. “允许所有网站”仍然受来源白名单约束；指定目标模式同时匹配来源与目标。
4. 允许规则后紧跟 SOCKS5 专用 `reject`，不能依赖出站文件顺序阻断流量。
5. 这组规则整体位于其他可能终结路由的规则前。数字前缀仅辅助排序，最终以合并数组的顺序断言为准；手工前置规则可能绕过保护时应停止发布并说明冲突。

下例表示只允许 `192.0.2.10/32` 访问任意目标，省略了可选的 sniff/resolve；文档地址是示例，实施时替换为用户输入：

```json
{
  "route": {
    "rules": [
      {
        "inbound": ["socks5_inbound"],
        "source_ip_cidr": ["192.0.2.10/32"],
        "action": "route",
        "outbound": "01_direct_outbound"
      },
      {
        "inbound": ["socks5_inbound"],
        "action": "reject"
      }
    ]
  }
}
```

指定目标模式将 `domain_suffix`、`domain` 或 `rule_set` 条件加在允许规则上。域名与 rule-set 两种目标需要表达 OR 时，展开为分别带相同来源条件的允许规则；不要通过错误的条件组合缩窄或放宽访问范围。原始目标 IP 的请求需以实际 sniff 结果验收，不能承诺任意 IP 连接都能识别出网站域名。

全新基础配置可以显式设置 `route.final="01_direct_outbound"`；SOCKS5 的拒绝由专用规则保证。混合部署保留原有 `route.final`、默认出站和其他入站规则。

### 5.3 配置生成边界

首次安装从空的候选目录生成基础配置、`20_socks5_inbounds.json` 和 `00_socks5_guard.json`。已有 sing-box 配置时复制现有片段，只补充必要项及更新本功能文件；本版本生成的 SOCKS5 配置可继续修改。

不提取或转换旧版 SOCKS5 的来源、目标和凭据，不增加旧配置迁移分支，也不因为发现旧版配置而重装内核或清空整个 sing-box 配置目录。现存配置导致候选配置检查失败时，报告错误并保留原配置和服务。

通过本功能专用生成器建立候选配置，不调用会额外安装其他协议的 `initSingBoxConfig()`，也不调用 `cleanUp singBoxDel/xrayDel`。

## 6. 事务、服务与失败恢复

建议新增 `installSocks5InboundStandalone()` 统一编排；“修改入站”和“修改规则”复用同一提交机制。

```text
检查前置条件/收集并校验输入
  → 准备最小依赖和内核
  → 重新检查端口及当前配置状态
  → 在 conf 同级的私有暂存目录生成候选配置
     （首次安装从空目录生成；已有配置时复制现有片段）
  → merge 到暂存主配置 → check → 检查最终路由顺序
  → 记录服务状态及新增防火墙规则；已有配置的增量修改备份本次涉及的文件
  → 提交配置 → 注册服务 → 应用端口规则 → 启动或重启 sing-box
  → 确认服务、进程和监听端口 → 启用自启 → 报告成功
任一步失败 → 返回非零并报告失败
  已有配置的增量修改：恢复本次变更及原服务状态
  首次安装：清理本次失败产物，保留有效下载文件供重试
```

实现约束：

- 暂存和备份不能放在会被 `-C config/` 扫描的 JSON 目录内。并发执行、配置锁和多进程竞争处理不在本次实现范围内。
- 通过 `generateSocks5InboundConfig()` 在候选目录补齐缺少的 local DNS、direct 和按需 HTTP Client；不调用会改写共享文件的无参数初始化函数。检查函数直接对候选目录执行 `merge/check`，不能调用会修改正式目录的无参数合并函数。原初始化函数保留原行为。
- 首次启动前先保存有效 `conf/config.json`，解决 `readInstallType → reloadCore` 的首次启动识别循环。此功能只操作 sing-box，不调用会连带重启 Xray 的 `reloadCore()`。
- 在 SOCKS5 安装事务中，将服务注册、启动和启用自启按顺序执行并逐项检查返回值。可为 `installSingBoxService()` 增加内部的延后启用参数：systemd 注册后先 `daemon-reload`，实际启动并确认入站可用后再 `enable`；OpenRC 同样在确认成功后加入启动级别。该参数仅用于事务编排，不形成独立用户操作。其他调用的默认行为保持兼容，已有服务的运行与自启状态纳入备份和恢复。
- 为 `handleSingBox()` 增加内部的“使用已验证配置启动”模式，或新增等价服务操作函数。该模式仅调用 systemd/OpenRC 启动服务，不执行 `singBoxMergeConfig()`、DNS/HTTP Client 初始化或其他文件写入；通过返回非零报告失败。安装提交后及失败恢复后均使用这一模式，确保启动的主配置就是已检查或已恢复的文件。其他既有调用保留原默认行为。补齐具体 service 状态与本次端口检查，不能仅靠宽泛的 `pgrep -f sing-box`，也不能因 `exit 0` 被误判成功。
- 已有服务定义默认复用，不在每次添加 SOCKS5 时覆盖。配置不兼容此服务的实际启动路径时明确提示；新建定义才采用脚本标准目录。
- 防火墙只增加本次端口所需规则，不改变默认策略，不清空已有规则；若复用的 helper 无法报告实际变更/失败，需要补齐接口。SOCKS UDP 行为以当前 sing-box 支持和实测为准，首期必验 TCP CONNECT，界面不承诺未经验证的 UDP 能力。
- 已有配置的增量修改涉及多个片段时，记录逐项恢复清单；主配置用同文件系统临时文件原子替换。配置检查成功前不停止现有服务，整个流程不替换已有核心二进制。
- 已有配置的增量修改失败时，只回滚本次变更，恢复原配置、自启和运行状态，并通过“使用已验证配置启动”模式启动原服务。首次安装失败时，清理本次新增防火墙规则及无效配置，停止本次新建服务并取消其自启，明确提示从原入口重试。有效的新二进制可以保留为“初始化未完成”；系统依赖包不自动卸载。恢复失败保留私有备份并显示路径，不输出安装成功。

## 7. 卸载与后续管理

修正 `removeSocks5Routing()`，按精确文件清单删除本版本生成的入站和 guard 配置，不新增旧版配置识别或迁移分支。清理 DNS/HTTP Client/direct 等共享片段前先检查剩余引用。

- 仍有其他 sing-box 入站：重新生成并验证配置，只重载 sing-box，其他入站继续工作。
- 删除最后一个入站：停止服务并禁用自启，不在同一分支尾部又调用通用 `reloadCore()` 把空服务启动。有效二进制和仍适用的共享基础片段可以保留供再次安装时复用；这是卸载后的残留处理，不提供空内核运行或管理模式。
- Xray + SOCKS5：只删除 sing-box 的 SOCKS5 片段，不停止或清理 Xray。
- 关闭端口只删除本功能确认拥有的规则，不删除预先存在的规则。若无法确认规则归属则保留并提示。
- 安装成功后，现有 sing-box 核心升级、停止、启动和日志入口继续可用；没有有效业务入站时提示先配置入站，避免残留文件被当作可用服务。

## 11. 实施记录与本地验证

2026-10-30 已完成中英文脚本同步实现，入口编号保持不变：

- `installSocks5InboundTools()` / `prepareSingBoxCoreForSocks5()` 检查运行环境和缺失依赖；仅在标准路径没有二进制时下载安装。已有不可执行文件直接报错。
- `generateSocks5InboundConfig()` 在私有候选目录补缺共享配置并生成入站、来源前置拒绝、目标允许与最终拒绝规则；不使用旧 block 出站。支持域名后缀、具名 geosite/rule-set 和全部目标。
- `checkSocks5Candidate()` 使用现有二进制 merge/check，并检查合并后的路由顺序。sing-box 会将单元素数组规范化为字符串，顺序检查兼容这两种输出形式。
- `commitSocks5Inbound()` 统一处理安装、规则替换和卸载；校验成功后才停止原服务。保存配置及服务运行/自启状态，失败恢复原主配置并直接启动，不重新初始化或合并。恢复失败则保留私有备份路径。

- 防火墙记录本功能新建的 TCP 规则，失败回滚或卸载时按归属清理。预先存在的规则不纳入删除清单；重复安装更换端口时，已托管的旧端口规则保留在清单中，最终卸载统一清理。
- 卸载最后一个入站时停止并禁用服务，保留有效核心及共享基础片段；其他入站仍存在时保留其配置。共享 DNS、direct 和 HTTP Client 片段保留，避免删除其他功能使用的对象。
- 补齐 SOCKS5-only、残留 Xray 和双核心状态识别，并保护账号、订阅、证书入口。核心管理菜单的停止/启动/重启直接使用已验证主配置；日志切换使用不额外初始化共享 HTTP Client 的合并方式。
